## Confirmed findings

### P0 — Requirements mismatch: price is still ₹199
- `src/app/components/pages/PricingPage.tsx` displays ₹199.
- `supabase/migrations/20261017170000_set_sem1_bundle_price_199.sql` sets published Semester 1 bundles to 199.
- The current UI still advertises the old bundle structure.
- **Required fix:** update the UI, all purchase/checkout price sources, server-side amount validation, and migration strategy together; add regression tests proving client-supplied amounts cannot override the server price.

### P0 — Referral reward is not the requested ₹25 cash reward
- Pricing still lists “Most Repeated Questions (Referral Reward)” as excluded.
- Existing referral dashboard/reward logic was built around three referrals unlocking notes.
- **Required fix:** implement a server-authoritative, idempotent ₹25 reward ledger triggered only after an eligible purchase is manually verified; define withdrawal/settlement handling and anti-self-referral/duplicate-purchase rules. Do not merely replace frontend wording.

### P1 — Preview deployment was skipped
- Workflow run: [Exam Kits Preview Deployment](https://github.com/AtharvaG0007/BCA-VAULT/actions/runs/39142983796)
- Passed: install, typecheck, build, output verification, API/CORS smoke tests.
- Skipped: deploy separate Cloudflare Worker.
- **Required fix:** configure and validate repository deployment secrets in GitHub Actions, then verify the deployed preview URL and its actual behavior. Do not deploy the feature to production as a substitute for preview validation.

### P1 — Authenticated critical-path E2E is missing
Must be tested using controlled test accounts:
1. Student signs in and creates an order.
2. Invalid plan/amount and malformed input are rejected.
3. Student submits payment evidence.
4. Student cannot access another student's order/evidence.
5. Non-admin cannot list or review orders.
6. Admin rejects an order; access is not granted.
7. Admin approves only after independent bank/UPI verification.
8. Entitlement is granted once and only once.
9. Student can access only purchased/published content.
10. Duplicate approval, repeated UTR, replayed requests and concurrent review are handled safely.

### P1 — Supabase security advisor findings need triage
The live security advisor reported:
- Three SECURITY DEFINER functions executable by the `anon` role: `get_or_create_referral_code()`, `handle_new_user()`, and `resolve_referral_identifier(...)`.
- Six SECURITY DEFINER functions executable by `authenticated`; each must be checked for intended exposure and caller validation.
- Leaked-password protection is disabled.
- RLS-enabled tables without policies were reported; some may be intentionally inaccessible, but that intention must be verified.
- A mutable search path warning exists for `update_referral_codes_updated_at`.
- `pg_trgm` is installed in `public`.

**Required fix:** inspect function definitions, grants, RLS policies, and intended access before changing permissions. Do not blindly add permissive policies or revoke grants without regression tests.

### P2 — Performance advisor warnings
The advisor reports foreign keys without covering indexes, RLS policies re-evaluating auth functions per row, and multiple permissive policies. Review against real query patterns and test after any changes; avoid speculative indexes or broad policy rewrites.

## Required release gate to reach at least 9/10

1. Implement ₹100 consistently in UI, database, and server-authoritative checkout logic.
2. Implement ₹25 referral rewards as an auditable, idempotent backend ledger; remove the old “three referrals unlock notes” reward flow without breaking existing legitimate records.
3. Add automated tests for price boundaries, referral qualification, idempotency, permissions, ownership isolation, and order review.
4. Configure preview deployment; verify the preview URL and inspect logs.
5. Run authenticated student/admin end-to-end tests, including rejection and duplicate/concurrent review cases.
6. Triage the Supabase security findings and re-run advisors.
7. Run production smoke tests and mobile/responsive checks after a controlled release.
8. Re-run CI after each fix. Do not merge while any P0/P1 remains or any critical-path test is unverified.
